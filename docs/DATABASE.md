# Database and auth

Postgres, accessed through SQLAlchemy 2.0 (async, asyncpg) with Alembic
migrations. Three tables: `users`, `conversations`, `messages`.

```
users ─1:N─▶ conversations ─1:N─▶ messages
```

---

## Schema

### `users`

| column | type | notes |
|---|---|---|
| `id` | `uuid` PK | `gen_random_uuid()` |
| `email` | `varchar(320)` UNIQUE | stored lower-cased |
| `password_hash` | `text` | bcrypt, cost 12 |
| `display_name` | `varchar(100)` NULL | |
| `is_active` | `boolean` | default `true` |
| `created_at` | `timestamptz` | default `now()` |

**UUID rather than `bigserial`.** This id goes into the JWT `sub` claim and into
URLs. A sequential integer would tell anyone who signs up roughly how many users
exist, and would make guessing other ids trivial. The cost is that random v4
values scatter across the B-tree instead of appending to it, so the index packs
less tightly — irrelevant at user-table scale, and specifically *not* irrelevant
for `messages`, which is why that table is different.

**Email lower-cased at the API boundary**, with a plain `UNIQUE` index — rather
than the `citext` extension or a functional index on `lower(email)`. Normalizing
in one function means every later query is a plain equality on a plain column:
no extension to install in each environment, no functional index that every
future query has to remember to match. The normalizer is
`api/routes_auth.py::_normalize`, and it is the only place that rule lives.

**320 characters** is the RFC 5321 maximum: 64-char local part, `@`, 255-char
domain.

**`is_active` instead of deleting rows.** Deleting a user cascades their entire
history away; that should be a deliberate, separate operation, not the way you
suspend an account.

**`timestamptz`, never `timestamp`.** A naive timestamp is a bug waiting for the
first deploy outside UTC.

### `conversations`

| column | type | notes |
|---|---|---|
| `id` | `uuid` PK | |
| `user_id` | `uuid` → `users.id` | `ON DELETE CASCADE` |
| `title` | `varchar(200)` NULL | derived from the first message |
| `created_at` | `timestamptz` | |
| `updated_at` | `timestamptz` | bumped on every new message |

index: `(user_id, updated_at DESC)`

**Ownership is a column, not an assumption.** Every read path filters on
`user_id`; there is no code path anywhere that fetches a conversation by id
alone. The helper that enforces it is `routes_chat.py::_owned_conversation`.

**`title` is nullable** because it is not known until the first message arrives.
`NULL` says that honestly; an empty string would not.

**`updated_at` is denormalized on purpose.** Sorting a thread list by "most
recent activity" would otherwise need `MAX(messages.created_at)` grouped per
conversation — an aggregate over the largest table, on every page load. One
extra column write per message replaces that with a plain index scan, and the
composite index above matches the query exactly.

### `messages`

| column | type | notes |
|---|---|---|
| `id` | `bigint` PK | `GENERATED BY DEFAULT AS IDENTITY` |
| `conversation_id` | `uuid` → `conversations.id` | `ON DELETE CASCADE` |
| `role` | `varchar(16)` | `CHECK (role IN ('user','assistant','system','tool'))` |
| `content` | `text` | |
| `meta` | `jsonb` NULL | citations, token counts, model, latency |
| `created_at` | `timestamptz` | |

index: `(conversation_id, id)`

This is where the design stops being symmetric, deliberately.

**`bigint` identity, not UUID.** Messages are the append-heavy table — the one
that grows without bound. Random UUID keys fragment the B-tree on insert and
double the width of every index entry that references them (16 bytes vs 8). The
enumeration argument that justified UUIDs on `users` does not apply here,
because a message is never addressed globally: you reach it through its
conversation, and *that* id is an unguessable UUID behind an ownership check.
The UUID does the security work one level up; the message key only has to be
narrow, ordered, and fast.

**Order by `id`, not `created_at`.** Two messages written in the same
microsecond can tie on a timestamp, and a tie makes a page boundary
non-deterministic — rows can be skipped or repeated across pages. An identity
column cannot tie, so it is a total order for free.

**That same column is the pagination cursor:**

```sql
SELECT * FROM messages
WHERE conversation_id = $1 AND id > $2
ORDER BY id LIMIT $3
```

Keyset, not `OFFSET`. With `OFFSET`, page 500 makes Postgres walk and discard
the preceding 49 900 rows; with a cursor, every page costs the same index seek.

**`role` as `varchar` + `CHECK`, not a native `ENUM`.** Adding a value to a
Postgres enum is an `ALTER TYPE` with awkward transactional semantics; adding
one to a `CHECK` is a constraint swap Alembic writes cleanly. Enums are for
value sets that never change, and this one will — tool calls and function
results are already on the roadmap.

**`meta` as `jsonb`** carries the fields that vary by role and should not each
become a nullable column: citations for a grounded answer (`{form, section,
url}`), token counts, model name, TTFT. This project already measures those in
`scripts/load_test.py`. It is named `meta` and not `metadata` because
`metadata` is a reserved attribute on SQLAlchemy's declarative `Base`.

**`content` stays inline.** No side table for large bodies — Postgres TOASTs
oversized text automatically.

### Deliberately absent

- **`messages.user_id`** — derivable through the conversation. A second source
  of truth for ownership is a second thing that can disagree with the first.
- **Soft deletes on messages** — every query would need `WHERE deleted_at IS
  NULL` forever, and forgetting it once is a data leak. Add it when there is a
  product reason.
- **A `sessions` table** — tokens are stateless; see the trade-off below.

## Auth

Stateless JWTs, HS256, 30-minute expiry. `sub` is the user id; `typ` is pinned
to `"access"` so a refresh token can never be spent as an access token; `jti` is
the handle a revocation list would key on.

`decode_access_token` pins `algorithms=[...]` to the configured algorithm rather
than trusting the token's own header — accepting whatever the header asks for is
the classic JWT confusion bug (`alg: none`, or an HS256 token signed with a
known public RSA key).

**The trade-off, stated plainly: a stateless JWT cannot be revoked before it
expires.** Logging out, changing a password, or disabling an account does not
invalidate tokens already issued. Two things soften it here — the short expiry,
and the fact that `get_current_user` re-reads the user row on every request, so
`is_active = false` takes effect immediately. Closing it properly needs a
refresh-token table with rotation, which is its own piece of work rather than
something to half-build now.

Other details worth knowing:

- **bcrypt truncates at 72 bytes.** The signup schema rejects longer passwords
  instead of accepting one whose tail is silently ignored — otherwise two
  different long passwords can unlock the same account. The check counts
  *bytes*, not characters, because one emoji is four of them.
- **Login spends a bcrypt round even when the email is unknown**
  (`dummy_verify`), so a 401 for a nonexistent account is not measurably faster
  than a 401 for a wrong password. Without it, response latency is an account
  oracle.
- **The 401 body never says which half was wrong.** "No such user" and "wrong
  password" as distinct messages turn the login form into a registration check.
- **Signup lets the `UNIQUE` constraint decide**, catching `IntegrityError`
  rather than doing SELECT-then-INSERT. Two concurrent signups for one address
  both pass a prior existence check, and one still has to lose at the constraint.
- **Another user's conversation returns 404, not 403.** A 403 confirms the id
  exists, which is an existence oracle for other people's data.

## Endpoints

| method | path | |
|---|---|---|
| `POST` | `/auth/signup` | → 201 `{access_token, token_type, expires_in}` |
| `POST` | `/auth/login` | → 200 same shape |
| `GET` | `/auth/me` | → 200 `{id, email, display_name, created_at}` |
| `POST` | `/conversations` | → 201 `{id, title, created_at, updated_at}` |
| `GET` | `/conversations` | → 200 list, most recently active first |
| `POST` | `/conversations/{id}/messages` | → 201 `{id, role, content, meta, created_at}` |
| `GET` | `/conversations/{id}/messages` | → 200 `{messages[], next_cursor}` |

History takes `?after_id=<cursor>&limit=<1..500>` and returns oldest-first.
`next_cursor` is `null` when the page is the end of the conversation.

`/v1/*` stays reserved for the OpenAI-compatible inference passthrough, since
that is where a client SDK expects to find it. This app's own API is at the root.

## Running it

### 1. Start Postgres

```bash
docker compose -f docker-compose.dev.yml up -d
```

No Docker? Any Postgres 13+ works — a local install, or a hosted instance
(Neon, Supabase, RDS). Point `DATABASE_URL` at it, keeping the
`postgresql+asyncpg://` prefix.

#### Where the data directory goes, and one place it must not

The dev host here has no Docker, so it runs portable Postgres 16 binaries
directly:

```
C:\Users\shris\AppData\Local\finance-research-copilot\pgsql\    binaries
C:\Users\shris\AppData\Local\finance-research-copilot\pgdata\   the cluster
                                                               port 55432
```

```powershell
$pg = "$env:LOCALAPPDATA\finance-research-copilot"
& "$pg\pgsql\bin\pg_ctl.exe" -D "$pg\pgdata" -l "$pg\pg.log" `
    -o "-p 55432 -c listen_addresses=127.0.0.1" start
```

`%LOCALAPPDATA%`, deliberately, and **never `%TEMP%`** — including the per-session
scratchpad, which lives under it.

This is not a style preference. On 2026-09-12 the cluster was there, and
Windows' `\Microsoft\Windows\DiskCleanup\SilentCleanup` task ran at 11:39:27 and
deleted the database out from under a server that had been running healthily for
eight days. It removed, by age, every file it was allowed to: `postgresql.conf`,
most of `global/`, and the bulk of the system catalogs in all three databases —
along with `initdb`, `pg_ctl` and the whole of the installation's `lib/`.
Recently-touched files survived because Windows would not let it delete an open
handle, which is why the damage looked so arbitrary.

The first symptom was at 11:41:14:

```
ERROR: could not open file "base/1/2601": No such file or directory
```

Postgres reported this correctly and kept serving what it could still read, so
the failure surfaced as one oddly-failing test rather than as an outage. There
was no crash, no improper shutdown, and nothing wrong with Postgres. WAL replay
cannot help: it replays changes to pages in relation files, it does not recreate
deleted ones — and with `postgresql.conf` gone the server will not start far
enough to try.

The container deployment is not exposed to this (`docs/DEPLOYMENT.md`): `pgdata`
is a named Docker volume, and nothing prunes those by age. The transferable rule
is just the one above — a data directory must never live anywhere a cleaner
believes it owns.

### 2. Configure

```bash
cp .env.example .env
python -c "import secrets; print(secrets.token_urlsafe(48))"   # -> JWT_SECRET
```

The app boots without a `JWT_SECRET` and logs a warning at startup. That is for
development convenience only: with the default secret, anyone holding this
source can forge a token for any account.

### 3. Migrate

```bash
python -m alembic upgrade head
```

The DSN is not in `alembic.ini` — `migrations/env.py` reads it from the same
`Settings` object the app uses, so the service and its migrations cannot end up
pointing at different databases.

To review the SQL before it runs, or on a machine with no Postgres at all:

```bash
python -m alembic upgrade head --sql
```

### 4. Verify

```bash
python scripts/check_migration.py    # models and migrations agree (no DB needed)
python scripts/db_smoke_test.py      # full signup -> history flow (needs a DB)
```

### Changing the schema

```bash
python -m alembic revision --autogenerate -m "add whatever"
```

Autogenerate needs a live database at the current head. Always read the
generated file: Alembic detects added and dropped columns reliably, but it
cannot see a rename — it emits a drop plus an add, which silently discards the
column's data.

`env.py` sets `compare_type` and `compare_server_default`; without them, a
widened `VARCHAR` or a changed default is invisible to autogenerate and the
models drift away from the schema without anyone noticing.
